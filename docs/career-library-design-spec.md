# 求職資料庫設計規範

> 狀態：已確認的開發基線  
> 日期：2026-08-13  
> 範圍：首版只統一管理系統已經持久化的生成成果，不改變成果的生成邏輯。

## 1. 目標

把目前散落在履歷、JD 比對和面試助手頁面右上角的歷史成果，集中到一個結構清晰的“求職資料庫”。資料庫提供兩種檢視方式：

- **按職缺**：把同一職缺相關的職缺分析、客製履歷、面試準備和模擬面試/回顧收在一個職缺檔案中。
- **按分類**：把全部成果按履歷成果、職缺分析和面試資料分組展示。

兩種方式只是同一批資料的不同組織檢視，不建立副本，也不改變原始資料的歸屬。

## 2. 已確認的核心規則

1. 主導航新增“求職資料庫”，放在“投遞職缺追蹤”之後、“設定”之前。
2. “按職缺”和“按分類”都是資料庫列表頁，保留錄階的全域性側欄和頂欄。
3. 兩種列表頁使用**完全相同的資料卡片元件和卡片圖形**：
   - 相同尺寸、封面比例、邊框、間距、標題區、後設資料區和操作位置。
   - 統一使用錄階現有的中性檔案/檔案圖形，不根據“職缺分析”“面試資料”等類型另畫圖表、對話方塊或書本樣式。
   - 類型差異只通過標題、標籤、關聯職缺、更新時間和內容摘要表達。
4. 點選職缺卡片或成果卡片後，進入類似履歷編輯器的獨立全螢幕工作區。
5. 獨立工作區隱藏全域性側欄和全域性頂欄，只保留：
   - 頂部工作區工具欄；
   - 一層左側資料樹；
   - 一層右側正文區。
6. 不允許出現“全域性側欄 + 內部資料樹”的雙層側欄，也不把資料樹套在第二層面板中。
7. “通用”不是資料類型，而是資料與職缺的關聯範圍：
   - 通用履歷優化屬於“履歷成果 / 通用優化”，不關聯職缺；
   - JD 優化履歷屬於“履歷成果 / 職缺客製”，關聯一個職缺；
   - 不設定“通用資料”分類或佔位卡片。

## 3. 首版納入範圍

| 使用者看到的成果 | 分類 | 職缺關係 | 首版處理 |
| --- | --- | --- | --- |
| 通用履歷優化 | 履歷成果 / 通用優化 | 無 | 納入 |
| JD 客製履歷 | 履歷成果 / 職缺客製 | 有 | 納入 |
| 原始 JD | 職缺分析 | 有 | 納入；資料庫不把自動提取的關鍵字、要求、風險和建議作為獨立檔案 |
| 面試準備資料 | 面試資料 / 面試準備 | 有 | 納入 |
| 模擬面試、回答與 AI 回顧 | 面試資料 / 模擬面試與回顧 | 有 | 納入 |

首版不納入：

- 原始履歷：它不是系統生成成果，繼續由履歷編輯器管理。
- 投遞記錄和追蹤日誌：它們屬於求職流程狀態，不是資料成果。
- 求職信、招呼語：當前只儲存在彈窗元件狀態中，重新整理或關閉後不會持久化；在增加正式儲存能力之前，資料庫不得展示虛假入口。
- 匯出的 PDF、DOCX：匯出檔案是下載結果，不在資料庫中再次儲存一份。

## 4. 資訊架構

### 4.1 資料庫列表頁

頂部結構固定為：

1. 標題“求職資料庫”；
2. 說明“按職缺或分類整理你的生成成果”；
3. “按職缺 / 按分類”分段切換；
4. 搜尋；
5. 資料分類篩選（全部資料、職缺分析、履歷成果、面試資料）；
6. 網格/列表檢視切換；
7. 資料卡片內容。

預設進入“按職缺”，使用者切換檢視後可在當前會話中保留選擇。

### 4.2 按職缺

每張卡片代表一個職缺檔案，而不是一條新的資料庫記錄。卡片至少顯示：

- 公司與職缺名稱；
- 當前投遞階段（存在投遞記錄時）；
- 最近更新時間；
- 職缺分析、客製履歷、面試準備、模擬面試的數量。

只有至少包含一項已持久化生成成果的職缺才進入資料庫。卡片主體整體可點選；首版不提供“刪除整個職缺檔案”，避免誤刪職缺、投遞和面試資料。

職缺列表按公司形成視覺分組。同一公司的不同職缺仍保留獨立職缺卡片，不合並職缺資料；公司識別只使用高置信度名稱歸一化，例如忽略空格、標點以及“有限公司”“Co., Ltd.”等法人後綴，不能僅憑名稱字首相似就強行合併。

### 4.3 職缺檔案工作區

進入職缺後採用獨立全螢幕工作區：

- 頂部：關閉、職缺名稱、狀態、關聯履歷、匯出、新增資料等操作；
- 左側資料樹：固定展示“職缺分析 / 履歷成果 / 面試資料”三個一級分類，讓檔案結構始終清晰；三個分類預設收起；
- 右側：顯示當前選中節點的正文。

建議樹結構：

```text
職缺檔案
├─ 檔案概覽
├─ 職缺分析
│  └─ 原始 JD
├─ 客製履歷
│  └─ {客製履歷名稱}
├─ 面試準備
│  └─ {準備資料名稱}
└─ 模擬面試與回顧
   ├─ {第 N 次模擬}
   └─ {對應回顧，存在時}
```

三個一級分類即使暫時沒有成果也必須保留，並在分類內顯示簡短的“暫無資料”說明；分類下的具體成果和成果內部節點仍只根據真實資料生成，不能補造不存在的內容。

### 4.4 按分類

按分類頁與按職缺頁使用同一外層佈局和同一資料卡片，不使用二級管理面板。內容按標題分段：

1. **履歷成果**
   - 通用優化；
   - 職缺客製。
2. **職缺分析**
3. **面試資料**
   - 面試準備；
   - 模擬面試與回顧。

每個分段顯示分組標題、數量、“檢視全部”和成果卡片。“檢視全部”只應用分類篩選，不進入樹狀工作區；點選具體成果卡片才進入成果工作區。

### 4.5 成果工作區

成果工作區與職缺檔案使用相同的全螢幕框架，但左側樹只描述當前成果自身的結構。

#### 通用履歷優化

```text
優化資料
├─ 優化概覽
├─ 履歷診斷（有診斷資料時）
│  ├─ 診斷結論
│  ├─ 已有優勢
│  └─ 問題清單
├─ 優化後履歷
└─ 修改記錄（有記錄時）
   ├─ 個人簡介
   ├─ 工作經歷
   ├─ 專案經歷
   └─ 技能
```

#### JD 客製履歷

```text
客製資料
├─ 優化概覽
├─ 職缺關聯
├─ 優化前履歷
├─ 優化後履歷
└─ 修改對比
```

#### 原始 JD

```text
原始 JD
```

#### 面試準備

```text
面試準備
├─ 能力輪廓
├─ 證據與差距
├─ 核心知識
├─ 經歷深挖
├─ 針對性問題
├─ 準備計畫
└─ 自我介紹與反問
```

#### 模擬面試與回顧

```text
模擬面試
├─ 模擬概覽
├─ 問題與回答
│  ├─ 問題 1
│  └─ 問題 N
└─ AI 回顧（已完成且存在反饋時）
```

歷史記錄缺少診斷、修改記錄或回顧時，目錄只顯示真實存在的內容，不能推測或補造。

## 5. 卡片規範

所有職缺卡片和成果卡片共享一個視覺骨架：

- 桌面網格預設兩列；列表模式只改變佈局，不改變資訊層級。
- 卡片頂部使用同一套低對比度檔案封面圖形。
- 卡片正文依次為標題、類型/狀態、關聯職缺（如有）、更新時間、內容摘要或數量。
- 卡片主體是主要開啟入口；刪除等危險操作放入更多選單並要求確認。
- 不為資料類型增加獨立彩色主題、不同封面插畫或不同卡片結構。
- 不使用大面積漸變、玻璃效果、厚陰影和卡片套卡片。

## 6. 搜尋、排序和狀態

- 搜尋範圍：成果名稱、公司、職缺、資料類型和摘要；不在首版對長正文做全文索引。
- 預設仍按最近更新時間展示；職缺檔案的更新時間取其全部成果中的最大值。列表右側不再單獨提供排序下拉，而是提供資料分類篩選。
- 空狀態區分：完全沒有成果、當前分類為空、搜尋無結果。
- 資料被其他頁面刪除後，資料庫立即反映；深連結指向已刪除記錄時顯示“資料不存在或已刪除”，並提供返回資料庫。
- 載入失敗不能回退為偽造樣例資料。

## 7. 響應式行為

- 桌面端：完整全域性側欄；列表兩列；工作區固定資料樹。
- 平板端：卡片可降為一列；資料樹允許收窄。
- 手機端：沿用現有移動頂欄；工作區資料樹收進抽屜，正文保持單列，不同時擠壓顯示樹和正文。

## 8. 入口遷移

資料庫上線後：

- 移除頁面右上角用於瀏覽全部優化版本、面試資料和面試記錄的歷史下拉入口。
- 各生成流程完成頁保留與當前任務直接相關的操作，例如“檢視本次成果”“進入編輯器”“前往資料庫”。
- 不同時維護兩套完整歷史列表，避免使用者繼續面對重複入口。

## 9. 驗收清單

- [ ] “求職資料庫”位於“投遞職缺追蹤”之後。
- [ ] 按職缺和按分類列表使用同一資料卡片及同一封面圖形。
- [ ] 按分類頁只有分組標題和卡片，沒有內部側欄。
- [ ] 職缺與成果詳情隱藏全域性側欄和頂欄。
- [ ] 詳情頁只有一層資料樹和一層正文。
- [ ] 通用優化歸入“履歷成果 / 通用優化”，不出現“通用資料”。
- [ ] 同一成果不會因為兩種檢視方式而產生兩份資料。
- [ ] 歷史記錄只顯示實際存在的結構化內容。
- [ ] 當前未持久化的求職信和招呼語不進入資料庫。
